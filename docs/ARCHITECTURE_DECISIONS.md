# Architecture Decisions — locked at Phase 2

Date: 2026-10-23. Host: Windows 25H2, go1.26.5, Node v24.16.0, Docker 29.7.2 / Compose v5.5.0.
Each ADR records the decision, the **evidence actually measured** (marked 🔬), the rationale, and the rejected alternatives. Version-sensitive links were retrieved 2026-10-23 and must be re-verified at upgrade time.

---

## ADR-001 — Repository boundary and git discipline
**Decided:** a new repository, initialized on branch `main`, independent of the upstream project. It had no remote at initialization; its later authorized publication uses a separate repository and never points at upstream.
**Why:** upstream `origin` has *push* access to the author's repository (Phase 1 audit §1); a stray push would be an act of vandalism on someone else's project. A history-less repo also makes the "original implementation" claim structurally true, not just rhetorically.
**Rejected:** fork (keeps upstream history and invites comparison-clone perception); working inside the clone (blurs provenance).

## ADR-002 — Codename "Fathom"; no public brand yet
**Decided:** internal codename **Fathom** (a unit of depth — fitting for depth-inspectable workflows). Directory/module naming uses `fathom`. Final branding is deferred to Phase 7 and requires a fresh conflict check.
**Evidence 🔬:** collision search 2026-10-23: "Cadence" collides with Uber's workflow engine and an existing health product → the Phase 1 proposal name is **retired**. "Fathom" collides only with unrelated categories (AI notetaker fathom.ai, accounting BI fathomhq, fisheries software) — acceptable for an internal codename, risky for a public dev-tool name; hence the rebrand gate.
**Rejected:** Cadence (direct collision with a workflow engine — fatal for a portfolio piece in the same category).

## ADR-003 — Build the engine; do not adopt Temporal/Cadence
**Decided:** implement a focused workflow engine (state machine, leases, timers, retries, compensation, DLQ) as the core deliverable.
**Why:** the engine *is* the portfolio artefact; Phase 1 produced a concrete, reproduced defect list the engine must solve, which converts into named regression tests (`AT-01…AT-10`). Adopting a complete engine would reduce the project to integration and remove the ability to demonstrate internal guarantees.
**Rejected:** Temporal/Cadence/Camunda — mature and correct, but they'd re-create solved problems *outside* the demonstrable scope; revisit only if the goal shifts from engineering proof to productising fast.
**Risk accepted:** we re-discover engine bugs. Mitigation: the state machine is a pure function over one row + version, property-tested (`TP-` tests) before any transport exists.

## ADR-004 — Go backend, single module, `CGO_ENABLED=0` for ordinary development
**Decided:** Go 1.26.5 host toolchain; one module `github.com/Lakhyajit-96/fathom` (root `go.mod`, binaries under `cmd/`, engine under `internal/`); every ordinary build/test path works with CGO disabled on Windows and cross-compiles for Linux.
**Evidence 🔬:** Phase 1 baseline §2 — the audited repo's `go build ./...` **fails on this host** because `confluent-kafka-go` needs CGO/librdkafka (DS-12 class). The chosen stack (ADR-005 probe) built with exit 0 under `CGO_ENABLED=0` on windows/amd64 and under `GOOS=linux` for amd64 and arm64.
**Rejected:** multiple modules per service (version-lock friction with no deployment benefit at this size); microservice-per-domain split of the control plane (the control plane is one deployable; participants are separate *processes*, same module).
**Phase 3 update (verified 🔬):** the product module `github.com/Lakhyajit-96/fathom` ships with **one external dependency** (`github.com/google/uuid`, ADR-018); everything else in the foundation is stdlib. A separate **`tools/` module** (`github.com/Lakhyajit-96/fathom/tools`) holds non-product probes so the product module stays minimal: `tools/portprobe` (the ADR-005 blank-import portability matrix, moved from `tools/depprobe` and renamed) and `tools/kafkasmoke` (the franz-go round-trip verifier). Being a nested module, `tools/` is excluded from the product module's `go build ./...`/`go test ./...`, so product CI never pulls the heavy probe dependency graph. `CGO_ENABLED=0 go build ./...` was re-run in Phase 3 for both modules: **exit 0** on windows/amd64 and cross `GOOS=linux` amd64+arm64.
**Phase 4 update (verified 🔬):** the durable PostgreSQL store (ADR-008) is a **product** responsibility, so the product module now carries **three** pinned direct dependencies: `github.com/google/uuid` (unchanged), plus `github.com/jackc/pgx/v5` **v5.11.0** and `github.com/golang-migrate/migrate/v4` **v4.20.1** (the migrator wraps pgx's `stdlib` driver, so PostgreSQL remains a single client dependency). Both additions are pure Go, so the ADR-004 CGO-disabled invariant still holds: Phase 4 re-ran `CGO_ENABLED=0 go build ./...` on windows/amd64 and cross `GOOS=linux` amd64+arm64 for both modules — **exit 0** each. `testcontainers-go` was **not** moved into the product module; the T-INT tier runs against a disposable `postgres:17.11-alpine` container started out-of-band (see `docs/PHASE_4_VALIDATION_REPORT.md`). This supersedes the Phase-3 "one external dependency" count, which was foundation-scoped, not permanent.
**Phase 5 update (verified 🔬):** the outbox relay (ADR-005/006) and the Prometheus metrics surface (ADR-015) bring **two more** pinned direct dependencies into the product module: `github.com/twmb/franz-go` **v1.22.2** (the relay's Kafka publisher) and `github.com/prometheus/client_golang` **v1.25.0** (`/metrics`) — five direct deps in total. Both are pure Go, so the CGO-disabled invariant was re-proven, not assumed: `CGO_ENABLED=0 go build ./...` on windows/amd64 plus cross `GOOS=linux` amd64+arm64 — **exit 0** each (see `docs/PHASE_5_VALIDATION_REPORT.md`). Kafka remains **optional at runtime**: the binary starts a producer only when `FATHOM_KAFKA_BROKERS` is set; a relay mode without brokers **refuses to start** rather than faking a sink. `franz-go/pkg/kadm` stays probe-only in `tools/` (no admin ops in the product path yet).

## ADR-005 — Kafka client: **franz-go** (measured decision, not taste)
**Decided:** `github.com/twmb/franz-go` v1.22.2 (kgo) + `pkg/kadm` v1.19.0 for admin ops, for the CDC-mode producer/consumer.
**Evidence 🔬 (2026-10-23, same host, `go build` exit codes):**
| Probe | Result |
| --- | --- |
| franz-go + pgx + otel + prometheus + chi + testcontainers, `CGO_ENABLED=0`, windows/amd64 | **exit 0** |
| same, `GOOS=linux/amd64` and `GOOS=linux/arm64` | **exit 0** |
| `confluent-kafka-go/v2` v2.16.0, `CGO_ENABLED=0`, windows | **fail** — package API compiled out (`undefined: kafka.Consumer` class) |
| same, `CGO_ENABLED=1` (no gcc on host) | **fail** — `cgo: C compiler "gcc" not found` |
**Rationale:** the v2 line is current and high-fidelity (based on librdkafka ≥ 2.13/2.16 — [confluent changelog](https://docs.confluent.io/kafka-clients/go/current/changelog.html), 2026-10-23), but it permanently reintroduces a native toolchain + librdkafka lifecycle — exactly the failure mode that made the audited repo unbuildable and un-reproducible. franz-go is pure Go, BSD-3, feature-complete through Kafka 4.x incl. idempotent/transactional producing and SCRAM ([repo](https://github.com/twmb/franz-go), 2026-10-23). Testability wins: unit tests can fake a broker-less producer without a C dependency.
**Rejected:** `confluent-kafka-go/v2` (CGO; proven above); `Segmenta kafka-go` (less active; no advantage here). Decision is *reversible* — the `Relay` interface (ADR-006) isolates the client.
**Phase 3 verification 🔬 (not just compile):** `tools/kafkasmoke` ran against a live `apache/kafka:4.3.1` broker and **PASSed**: kadm topic-create + produce (8 records) + consumer-group read-back with payload/header verification + manual offset commit. This exercised the exact primitives the Phase 4 relay needs — no claim is made from package names. API facts corrected during the run (franz-go's real surface, recorded so Phase 4 does not re-guess them): producers are **idempotent by default** (opt-out is `DisableIdempotentWrite`, there is no `IdempotentProducer`); all-ISR acks is `RequiredAcks(kgo.AllISRAcks())`; group commit is `CommitUncommittedOffsets(ctx)`; `Fetches` has no `IsUserStopped`. Transactional/EOS producing is available but **not used** — the design is at-least-once via the outbox + consumer dedup (ADR-011), so we do not depend on broker transactions.

## ADR-006 — Two relays, one interface
**Decided:** `Relay` interface with (a) **pgoutbox** — pure-Go poller (`SELECT … FOR UPDATE SKIP LOCKED` → produce → mark `published_at`), the default for dev/CI; (b) **cdc-debezium** — outbox table → Debezium connector → Kafka, the production-shaped demo mode. Shared conformance suite (§test plan T-RELAY) both must pass.
**Why:** Phase 1 verified the Debezium + Outbox EventRouter topology genuinely works (audit capability rows 1–2) — that strength is kept, not copied blindly; but forcing a 3 GB Kafka+Connect stack into every CI test is operational theatre. `published_at` + sequence cursor also fixes DS-9 (outbox never marked/pruned, replay accidental instead of intentional).
**Rejected:** Kafka-only (slow, flaky CI); pure-Go-only (throws away the audited CDC differentiator); NATS/NSQ (would be a new lesson, not a workflow lesson).
**Phase 5 implemented 🔬:** the **pgoutbox** relay is the shipped default (`internal/relay`): claim (`SELECT … FOR UPDATE SKIP LOCKED` on outbox rows with per-row claim leases) → produce via the `Publisher` interface → ack + single-row `relay_checkpoint` cursor, with bounded retry/backoff and a durable `RETRY_EXHAUSTED` DLQ row on permanent publish failure. Conformance is proven by tests incl. crash-after-publish-before-ack redelivery (R-T1), two-relay claim mutual exclusion (R-T2) and stale-owner ack refusal — the `cdc-debezium` alternative remains the compose smoke proof from Phase 3 and is not re-run here. The `Relay`/`Publisher` split keeps the Debezium mode swappable without touching the engine.

## ADR-007 — CDC mode infrastructure versions (pinned)
**Decided for the CDC relay (product compose comes in a later phase; `deploy/docker-compose.smoke.yaml` is the Phase-3 proof):** Kafka via official `apache/kafka` KRaft image (available since 3.7; [official docs](https://kafka.apache.org/41/getting-started/docker/), 2026-10-23), Debezium platform image `quay.io/debezium/connect:3.7.0.Final` (Debezium 3.7 = latest stable, 2026-09-29, [releases](https://debezium.io/releases/); images moved to quay.io exclusively since 3.0, [notice](https://debezium.io/blog/2024-09-18/quay-io-reminder/)), connector = built-in `PostgresConnector` with `OutboxEventRouter` SMT (still the documented mechanism, [Debezium outbox doc](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)). All images pinned by tag **and digest**; no `latest-*` (fixes DS-12's mutable-base lesson).
**Rejected:** the audited repo's `confluentinc/cp-*:7.4.1` + `strimzi:latest-kafka-3.4.0` + connector 2.4.1 tarball from a mutable URL (Zookeeper-era, EOL series, non-reproducible).
**Phase 3 resolution 🔬 (open item discharged):** the compatibility matrix was verified by an actual Docker Compose smoke test, not assumed. The pair is fixed to **`apache/kafka:4.3.1` + `quay.io/debezium/connect:3.7.0.Final` + `postgres:17.11-alpine`**, chosen from Debezium 3.7 release notes ("built against Kafka Connect **4.3.1** and tested with Kafka brokers **4.3.1**"), so the broker tag matches the Connect runtime exactly. Digests recorded in `docs/PHASE_3_VALIDATION_REPORT.md`.
**Smoke evidence 🔬 (`deploy/docker-compose.smoke.yaml`, loopback-bound, fake creds):** all three services reached *healthy*; the `PostgresConnector` + `OutboxEventRouter` connector reached **RUNNING** (connector **and** task); an inserted outbox row was routed to the `smoke.events` Kafka topic and read back with the expected key (`aggregate_id`), expanded JSONB payload, and the `eventType` header the SMT was configured to place. Reproducible via `scripts/cdc-smoke.sh` / `task cdc:smoke` and wired as the `cdc-integration.yml` CI job. Re-executed end-to-end in Phase 3 to `SMOKE PASS` with the exact routed record `key=agg-smoke`, `eventType:RoomReserved`, `__debezium.context.connectorLogicalName:fathomcdc`, value `{"ok":true,"wf":"fake"}`.
**Two cross-platform reproducibility bugs found by running the script on Windows (Phase 4's CI relies on this being the single source of truth):** (1) **Connect REST cold-start race** — `docker compose up --wait` returns once the container is *running*, but Kafka Connect keeps creating its internal config/offset/status topics and starting the REST listener for a while; a connector `POST` in that window returns an empty reply (measured `HTTP=000`, then `200`). The script now polls `GET /connectors` until `200` before registering. (2) **Git-for-Windows MSYS path rewrite** — running the script under Git-bash, `docker compose exec … /opt/kafka/bin/kafka-console-consumer.sh` had its in-container POSIX path mangled to `C:/Program Files/Git/opt/…` before `docker.exe` saw it, so the consume step failed. The script now `export MSYS_NO_PATHCONV=1` / `MSYS2_ARG_CONV_EXCL='*'` (a no-op on Linux). Both were only exposed by actually running on the Windows host — the routing had previously been confirmed manually, which masked them; this is the "environment-specific workaround" class §5 warns against, now designed out rather than papered over.
**Two Debezium-3.7 Outbox-EventRouter gotchas discovered (Phase 4's product outbox MUST honour them):** (1) `transforms.outbox.table.field.event.key` defaults to a column literally named **`aggregateid`** (no underscore) — with our snake_case `aggregate_id` it throws `"aggregateid is not a valid field name"` unless set explicitly; (2) `transforms.outbox.table.field.event.timestamp` requires an **INT64 epoch** column — a `TIMESTAMPTZ` column raises `"Field 'created_on' is not of type INT64"` and fails the task, so either omit the mapping or store the outbox timestamp as epoch-millis BIGINT.

## ADR-008 — Durable state: PostgreSQL 17, pgx/v5, golang-migrate
**Decided:** Postgres as the only consensus layer: workflow/step/attempt rows, leases, timers, idempotency, outbox, DLQ, audit — one transactional domain. Client `pgx v5.11.0` (+ `pgxpool`); schema via `golang-migrate` versioned SQL migrations (no init-only bind mounts — Phase 1 had no migration story). `btree_gist` + `daterange` EXCLUDE constraint for the inventory showcase.
**Evidence 🔬:** pgx resolves and builds in the probe (ADR-005 table); Phase 1 proved Postgres transaction semantics carry the outbox and dedup patterns correctly.
**Rejected:** Redis/ZK for locks (extra failure domain, no gain); Durable Objects (platform lock-in breaks portability of the engine claim); SQLite (no row-level locks/`SKIP LOCKED`, weak demo of concurrent-worker semantics).

## ADR-009 — Concurrency model: optimistic core + lease-based claiming
**Decided:** workflow rows carry `version`; **every** transition is `UPDATE … WHERE id=$1 AND version=$2` with `RowsAffected==1` required (fixes DS-4 — the audited repo incremented version but never used it). Workers claim steps with `SELECT … FOR UPDATE SKIP LOCKED` + `lease_expires_at` + monotonically increasing per-step `attempt` whose value **is** the fencing token participants must check. Multi-replica control plane and workers are safe by construction.
**Rejected:** Kafka consumer-group partitioning as the lock (couples workflow identity to topic topology; awkward replay — Phase 1 target-architecture §3 rationale stands); advisory locks without durable records.
**Phase 5 implemented 🔬:** the second half of this ADR is now real: `internal/worker` claims steps with `FOR UPDATE SKIP LOCKED` + `lease_expires_at` + monotonically increasing per-step `attempt` as the fencing token; heartbeats renew leases on TTL/3; an expired lease is **reclaimed** (bumped attempt) and the displaced worker's stale submission is rejected by the version guard — proven by contention tests (two workers, one claim; stale-after-reclaim refusal; heartbeat extension) under `-race` on native Linux. Multi-replica safety is exercised, not asserted.

## ADR-010 — Event contract & topic strategy
**Decided:** versioned JSON envelope (CloudEvents-inspired; exact fields in DATA doc §C) with mandatory identity block `event_id, workflow_id, step_type, attempt, causation_id, traceparent, specversion`. Topics: `fathom.commands.v1`, `fathom.results.v1`, `fathom.dlq.v1` — partition key = `workflow_id` (per-workflow ordering at any partition count; removes the audited 1-partition crutch, DS-11). Envelope validated at ingest; **reject-with-classification**, never reject-by-drop. Golden-file contract tests in CI. No schema registry (rejected: enforcement worth a whole extra service at this scale — Phase 1 target-arch trade-off 4 stands).

## ADR-011 — Idempotency layering
**Decided:** four explicit keys, four explicit stores (full table in DATA doc §D): client `Idempotency-Key` (API), `business_key` partial-unique (one active workflow per target), `(workflow_id, step_type, attempt)` (participant inbox, same tx as side effect), `event_id` (engine `processed_events`). Each layer names its on-duplicate behaviour. The audited repo proved layer 4 alone is not enough (DS-1: a re-authored event has a fresh id).

## ADR-012 — Guaranteed progress subsystem
**Decided:** deadlines are data (`deadline_at` on workflow, `response_timeout` per step), enforced by a **reaper** (multi-replica-safe via `SKIP LOCKED`), retry schedules are durable rows/columns (`next_attempt_at`), retry budgets are per-step-with-jitter, compensation failure escalates to `FAILED_MANUAL` + DLQ. `oldest_open_workflow_age_seconds` is a first-class metric and a CI gate input (closes DS-2, DS-6, scenario 10).
**Rejected:** relying on transport redelivery for progress (the audited system's only "timer" was human patience).
**Phase 5 implemented 🔬:** the reaper/scheduler loop ships (`internal/scheduler`): retry schedules are durable (`next_attempt_at`, scanned with the database clock — never a wall-clock in the process), backoff is bounded (2 s × 2^(n−1), cap 60 s, full jitter keyed on the durable row), response/compensation deadlines are stamped at issue time and escalate via W13, and every scan is `SKIP LOCKED`-guarded so multiple scheduler replicas are safe. `oldest_open_workflow_age_seconds` and the relay-lag gauge feed `/readyz` and `/metrics` from real queries.

## ADR-013 — AuthN/AuthZ model (demo-honest, not theatrical)
**Decided:** local-first single tenant; cockpit auth via session cookie + CSRF; API via bearer key; roles `reader` / `operator` / `admin`; operator actions require role + reason string + audit write incl. state snapshot. Passwords/keys from env only; demo credentials live in `.env.example` as obviously-fake values and are **never** read by code paths that could ship them (fixes the Phase 1 hard-coded-credential pattern). Full mapping in THREAT_MODEL.md.
**Rejected:** "no auth because demo" (kills the safe-operator product story); OIDC provider dependency (external service, billable or fiddly, adds no demonstrable boundary).
**Phase 5 partial (honest boundary):** the **API bearer-key half is implemented** — `FATHOM_API_KEYS` (`label:role:key`, env-only, `Secret`-wrapped, never logged), roles enforced per route (`reader ⊂ operator ⊂ admin`), every operator action carrying a mandatory `reason` + an `operator_action` audit write with the state snapshot, and audit `actor` = the authenticated key **label** (no invented identities). The **cockpit session/CSRF half belongs to the frontend phase** (deferred per the Phase-5 brief's no-frontend scope). Because bearer keys alone are not a public-internet boundary, the server **refuses any non-loopback bind** while this is the only control (`api.LoopbackOnly`) — documented in DEVELOPMENT §3 as "do not expose before full authN", not claimed as security.

## ADR-014 — Frontend stack
**Decided:** React **19.3.1** + Vite **8.3.5** + TypeScript (pinned at scaffold; TS 7.0.2 is newly released — pin the version Vite's template ships and verify before adopting 7.x), `@xyflow/react` **12.12.0** (MIT, actively published — npm registry 2026-10-23) for the execution graph, `@tanstack/react-query` **5.104.5** for server state, **SSE** (not WebSocket) for live updates.
**Why SSE:** the stream is one-way (mutations are REST + idempotency keys); `Last-Event-ID` reconnect maps directly onto our monotonic `audit_event.seq` — reconnection becomes a *demonstrable* property rather than a claim.
**Rejected:** Next.js (no SEO need; second runtime to operate); Redux (query-cache-shaped state); hand-rolled SVG graph; WebSocket (no client→server channel needed; harder reconnect semantics).

## ADR-018 — Identifier strategy: UUIDv7 via `google/uuid`
**Decided:** identifiers for workflows/steps/attempts/events/inbox keys are **UUID version 7**, generated through `github.com/google/uuid v1.6.0` (`NewV7`), rendered as canonical lowercase hyphenated text. A thin `internal/id` package owns the policy (always-v7, canonical form, injectable-entropy seam for tests) so the rest of the code never imports the library directly.
**Evidence 🔬:** stdlib has **no** RFC 9562 UUID facility — `crypto/rand` only yields raw bytes with no version/variant semantics or ordering, so a library is required. `google/uuid v1.6.0` ships `version7.go` with `NewV7()`/`NewV7FromReader(io.Reader)` and an in-process monotonic counter (verified from the module cache, not from memory); BSD-3-Clause, pure Go, already the Phase 2 pin.
**Why v7 (not v4):** the first 48 bits are Unix-millis, so ids sort by creation time — directly serving the data contract's time-ordered primary keys and cursor paging, and giving a total order that helps de-duplicate/dedupe reasoning. Uniqueness = 74 bits of randomness within the millisecond bucket + per-process monotonic sequence.
**Rejected:** `gofrs/uuid/v5 v5.5.1` (also supports `NewV7`/`NewV7AtTime`, MIT; rejected only because `google/uuid` is the existing pin and its `NewV7FromReader` already gives a deterministic test seam — revisit only if explicit-time vectors become necessary); `github.com/google/uuid` **v4-only** usage (throws away ordering); hand-rolled v7 (reinvents a spec detail, invites variant-bit bugs). Tests in `internal/id/id_test.go` assert version nibble `7`, RFC variant bits, uniqueness (10k), and the in-process strictly-monotonic ordering guarantee.
