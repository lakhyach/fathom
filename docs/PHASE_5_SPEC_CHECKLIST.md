## 2. Gaps found between documented guarantees and implemented code (§1.4), and how Phase 5 resolves them

1. **`TimeoutStep` missing CANCELLING guard (real defect path).** `engine.TimeoutStep` can move a `CANCELLING` workflow to `RETRY_WAITING` (edge not in the W-table), and the Phase-5 scheduler would then re-issue a *forward* attempt during cancellation. Fix: timeout under `CANCELLING` goes straight to the W7/W8 wind-down fork (same rule `applyForwardResult` already enforces for failure results). Regression test in engine + scheduler contention test.
2. **W15/W16 intermediate state.** The table has `CANCELLING → ABORTED/FAILED` but the wind-down runs through the compensation chain whose rows are written under `COMPENSATING`. Phase 4 implemented cancel-wind-down as CANCELLING→COMPENSATING→(W10 chain)→ABORTED, which yields exactly the §10 outcome set (never COMPLETED). Phase 5 keeps that interpretation (terminal outcomes identical, no new capability) — recorded here so the docs and code agree on the reading.
3. **`response_deadline_at`/`compensation_deadline_at` have no writer.** Columns exist since 0001 but nothing sets them; the reaper (§8) needs them. Phase 5 stamps them at issue time from per-step timeout durations (SM §8 defaults: 60 s), sourced from the definition snapshot; durations become additive columns on `step` (migration 0002, documented).
4. **`relay_checkpoint`, `operator_action`, `workflow_definition` absent by design** (Phase 4 scope note). Phase 5 needs all three → versioned migration 0002; 0001 is never edited.
5. **DLQ class `RETRY_EXHAUSTED` has no emitter.** The W-table routes forward-budget exhaustion to W7/W8 (defined outcomes), not to a manual queue; emitting operator work items for workflows that already reached their specified outcome would contradict §7 ("queue of durable operator work"). Phase 5 emits `RETRY_EXHAUSTED` from the **relay** when a row's publish retries are permanently exhausted (delivery exhaustion *is* operator work), and the class list stays schema-complete for the rest.
6. **Binary topology.** Roadmap M3.1 sketched `cmd/fathom-control|worker|relay`; implementation has one `cmd/fathom`. Phase 5 keeps ONE binary with modes (`fathom control|worker|relay|all`) — same module, shared internal packages, fewer mains; `all` is the local lite stack. Documented deviation, not invented auth.
7. **Dependency graph.** The ADR-mandated default relay publishes to Kafka (ADR-005/006) and ADR-015 norms Prometheus — Phase 5 adds `franz-go v1.22.2` and `client_golang v1.25.0` (both pure Go; CGO=0 re-proven) and amends the ADR-004/DEVELOPMENT dependency statements, exactly as Phase 4 amended them for pgx/migrate. Kafka remains *optional at runtime*: relay with no brokers configured does not start a producer.
8. **OTel SDK deferred.** ADR-015/REQ-OP-6 specify OTLP→Jaeger; brief §8 forbids traces not connected to real operations, and no collector runs in this phase's validation. Phase 5 implements the *contract-level* trace context (W3C `traceparent` minted into every outbox envelope, `causation_id` chains, `trace_id` in logs/errors) and defers the SDK exporter to the observability-depth phase with this reasoning recorded. No fake Jaeger claim anywhere.
9. **Auth boundary.** ADR-013/PRODUCT §7 define roles reader|operator|admin via bearer keys, cockpit session/CSRF belongs to the frontend phase (out of scope per brief §"no frontend"). Phase 5 implements the safe local-only boundary: API keys from `FATHOM_API_KEYS` (label:role:key, env-only, redacted in logs), loopback default bind, and documents loudly that the API must not be publicly exposed before full authN lands. No invented identities: audit `actor` = the authenticated key label.
10. **Phase-4 direct-ApplyResult path stays unleased.** Lease enforcement is opt-in via the new worker submission path (`SubmitResult` with claim identity) so the Phase-4 event-driven API (external participants answer without DB leases) remains valid; both paths classify through the same pure machine.
